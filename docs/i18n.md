# UI internationalization (i18n)

Zero-dep, framework-free runtime for translating the player and admin
shells. English (`en`) and Spanish (`es`) ship at parity. Adding a
new locale is a single JSON file plus updates in six locations — see
[Adding a new locale](#adding-a-new-locale) for the full checklist.
The list is small but distributed because the boot sequence touches
storage, the runtime, and both server-side gates independently; each
spot is checked by either CI or by the runtime's fail-soft fallback.

## Architecture

| Layer | File | Responsibility |
| --- | --- | --- |
| Runtime (browser) | `public/js/i18n.js` | Loads locale JSON, exposes `t()` / `formatDate()` / `formatNumber()`, applies `data-i18n` bindings to the DOM. |
| Locale resources | `public/locales/<lang>.json` | Nested namespace keys grouped by UI section (e.g. `create.startPuzzle`, `play.solvedFormat`). |
| Coverage gate | `scripts/i18n-coverage.js` | CI script invoked via `npm run i18n:check`. Asserts every `data-i18n` / `data-i18n-attr` / `i18n.t("…")` reference resolves in `en.json`, AND that `en.json` and `es.json` have identical key sets. |
| Server (HTTP error JSON only) | `lib/server-i18n.js` | Parses `Accept-Language` and translates the small set of error-JSON keys that surface to the player. Logs / admin output / persisted data stay English. |

## Player flow

1. Page load: a small inline `<script>` in `public/index.html` reads
   `localStorage.localePreference` directly, validates it against the
   shell's hardcoded `SUPPORTED = ["en", "es"]` allowlist, and sets
   `<html lang>` BEFORE the stylesheet — so screen readers and
   `:lang(es)` CSS see the right value on first paint (no FOUC). The
   snippet duplicates the allowlist on purpose: `i18n.js` itself is
   loaded with `defer`, so it isn't available yet at this point in
   the head. Keeping the allowlist inline avoids a render-blocking
   script just to gate one attribute.
2. After the deferred scripts run in source order — `i18n.js`, then
   `app.js` — `i18n.init()` fetches `/locales/en.json` (always, as
   fallback) and the active locale (if not `en`), then calls
   `updateDOM()` to translate every `data-i18n=` and `data-i18n-attr=`
   node. `app.js` awaits `window.i18nReady` before its first `t()`
   call so dynamic UI never sees a half-loaded message store.
3. The header has a language `<select id="uiLangSelect">`; switching
   it calls `loadLocale(next)` (which re-runs `updateDOM()` internally)
   and then re-renders any imperatively-built dynamic surface
   (challenge list, active summary panel, leaderboard) so its
   `i18n.t(...)` strings refresh too. No page reload required.

## Admin flow

Same as player except the inline pre-paint and the deferred script
ordering live in `public/admin/index.html`, the switcher is
`#adminUiLangSelect` in the workspace header, and the namespace prefix
`admin.*` carries admin-specific keys. The admin pre-paint duplicates
its own `SUPPORTED = ["en", "es"]` allowlist for the same FOUC reason.

## Locked decisions

| Topic | Behavior |
| --- | --- |
| **Locale code format** | BCP 47, lowercased base form (`en`, `es`). Future regional variants like `es-MX` would still store as `es` for the simple matcher. |
| **Resource format** | JSON, nested namespace keys. |
| **Key access** | Dot notation: `t("create.startPuzzle")`. Nested objects are walked left-to-right. |
| **Interpolation** | Single curly braces: `"Solved in {tries}/{max}!"`. Pass params as the second arg. Escape with literal `\\{`. |
| **Pluralization** | Keys carry suffixes (`_one`, `_other`, etc.); the resolver picks via `Intl.PluralRules.select(count)` when the call site passes a `count` parameter. |
| **Missing-key fallback** | Active locale → `en` → literal key. Optional `?i18nDebug=1` query string warns once per missing key in the console. |
| **Persistence** | `localStorage["localePreference"]`. Survives sessions and profile switches. |
| **DOM bindings** | `data-i18n="key"` for `textContent` (or `placeholder` on inputs). `data-i18n-attr="placeholder:key;aria-label:key"` for arbitrary attributes (semicolon-delimited). |
| **Switcher placement** | Player → header settings strip. Admin → workspace header (hidden until unlock). |

## Build / CI gate

`npm run i18n:check`:

- **Parity check**: `en.json` and `es.json` must have identical key sets — strict per-key equality, including each individual plural-suffixed key (`_one`, `_other`, etc.). Either-side missing keys fail the build so the runtime never has to fall back across locales mid-plural.
- **Reference check**: every `data-i18n=` / `data-i18n-attr=` / `i18n.t("…")` in the four scanned source files (`public/index.html`, `public/admin/index.html`, `public/app.js`, `public/admin/app.js`) must resolve to a key in `en.json`.
- **Orphan check**: keys present in `en.json` that no source references (and aren't in the `SOFT_ALLOW_PREFIXES` list for runtime/utility namespaces) fail the build.

The script is wired into `npm run check` so CI gates on it alongside lint, schema validation, and tests.

## Adding a new locale

1. Copy `public/locales/en.json` to `public/locales/<lang>.json`.
2. Translate every value (keys must stay identical — strict parity is
   enforced by `npm run i18n:check`).
3. Add `<lang>` to `availableLocales` in `public/js/i18n.js`.
4. Add an `<option>` to `<select id="uiLangSelect">` in
   `public/index.html` and `<select id="adminUiLangSelect">` in
   `public/admin/index.html`.
5. Add `<lang>` to the inline pre-paint `SUPPORTED` array in
   **both** `public/index.html` and `public/admin/index.html`. These
   arrays gate first-paint `<html lang>` and intentionally duplicate
   the runtime's allowlist (the inline snippet runs before `i18n.js`
   has had a chance to load).
6. Add `<lang>` to `SUPPORTED` in `lib/server-i18n.js` so HTTP error
   JSON honors `Accept-Language` for the new locale.
7. Update the locale-file paths in `scripts/i18n-coverage.js` (the
   parity check is hardcoded to `en.json` ↔ `es.json`; extend it to
   compare the new file as well, otherwise its keys won't be gated).
8. `npm run i18n:check` to verify parity, references, and orphans.

## Admin shell migration scope

The admin shell (player + admin) is migrated to `data-i18n` in the
HTML markup, but most JS-built dynamic content in `public/admin/app.js`
(provider table rows, runtime-config form fields, profile lists,
analytics summaries, schedule entries, etc.) is still written with
hardcoded English strings via `textContent`. Switching locales
**will not** translate those rows — they redraw with the same English
copy when the active tab's loader fires.

The language switcher's tab-reload hook is a forward-compat seam:
once a tab's renderer is migrated to `i18n.t(...)`, the switch will
pick up the new locale automatically. Migrating each admin tab is
incremental and tracked separately. The coverage script doesn't flag
this gap because the gap is "no `data-i18n` references for those
runtime-rendered cells" — there's nothing to scan against.

## Server-side scope

`lib/server-i18n.js` is intentionally minimal:

- `parseAcceptLanguage(headerValue)` — bounded parser (10 entries, 256 chars max) that returns the best supported base-language match; `en` if nothing matches.
- `translateForRequest(req, key, params)` — used by error-handling routes that want to surface a localized `error` field. Falls back to `en` then to the literal key.

It explicitly does NOT translate logs, persisted data, admin responses, or rendered HTML. Server output stays English.

## Test coverage

- **Unit**: `tests/i18n-runtime.test.js` — `t()`, interpolation, missing-key fallback, plural resolution (en + es via `Intl.PluralRules`), `formatDate` / `formatNumber` per active locale, `loadLocale` persistence, `bootstrapLang` reading + writing `<html lang>`.
- **Unit**: `tests/server-i18n.test.js` — `Accept-Language` parsing edge cases (q-factor ordering, ties, pathological input bounds), `translateForRequest` with and without header.
- **Coverage gate**: `npm run i18n:check` runs in CI alongside lint and tests; failures here fail `npm run check`.
